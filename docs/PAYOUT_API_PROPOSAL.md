# よあコイン API 改正提案（包括版）

対象: よあコインAPI 開発者
提案者: 「よあコイン 経済×コレクションBot」運営（一般会社）
日付: 2026-07-23

---

## 1. 背景と目的

現行API（`/payments` 等）では、会社は**入金の検知**はできますが、**会社からユーザーへよあコインを渡す**手段がありません（「お金＝よあコイン本体は動かせない。換金・支払は客本人がDiscordで行う」仕様）。

そのため、一般会社が

- ユーザーへ**報酬としてよあコインを付与**する（例: クエスト達成報酬・イベント配布）
- ユーザーが預けた分を**払い戻す（換金）**

ことができず、社長の手動 `y!` 運用に頼らざるを得ません（遅い・二重払いリスク・スケールしない）。

本書は、**カジノの `/chips` とは別に、一般会社が自社ユーザーへよあコインを付与/払い戻すためのAPI**を包括的に提案します。すべて**会社資金（準備金）を超える付与は拒否**されるため、既存の「裏付けのない発行はさせない」思想と整合します。

---

## 2. 推奨する通貨モデル（内部残高モデル）

当Botは以下の設計を採っており、これが**API負荷と会社資本の効率**の両面で最良と考えます。開発者側の実装判断の参考として共有します。

- 会社はユーザーの残高を**内部台帳**で管理する（1コイン = 1よあコイン）。
- **報酬付与・ゲーム内消費は内部残高の中で相殺**され、実よあコインは動かない。
- 実よあコインが動くのは **入金（ユーザー→会社）** と **出金（会社→ユーザー）** の2箇所だけ。

この方式なら、頻繁なゲーム操作ごとにAPIを叩く必要がなく、実送金は出金時の `POST /payout` 1回で済みます。したがって**最優先で必要なのは `POST /payout`** です。以下、包括提案として関連エンドポイントもまとめます。

---

## 3. 提案エンドポイント

### 3.1 `POST /payout`（中核: 会社→ユーザーのよあコイン付与）

会社の資金からユーザーへよあコインを渡す。用途は `kind` で区別する。

- 認証: 既存同様 `Authorization: Bearer yoak_...`（カジノ権限不要・一般会社で可）。
- リクエストボディ:

```json
{
  "user_id": 123456789,
  "amount": 4600,
  "kind": "withdraw",
  "idempotency_key": "b3f1c2a4-..."
}
```

| フィールド | 説明 |
|-----------|------|
| `kind` | `"withdraw"`＝預り分の払い戻し ／ `"reward"`＝資本金を報酬として付与。監査・集計用 |
| `idempotency_key` | 必須。冪等キー |

- 成功レスポンス（例）:

```json
{
  "payout_id": 91021,
  "user_id": 123456789,
  "amount": 4600,
  "kind": "withdraw",
  "company_balance": 25400
}
```

- **準備金チェック必須**: `company_balance - amount < reserve_floor` なら拒否（`400 insufficient_reserve`）。会社が設定可能な下限フロアがあると理想。
- **冪等性**: 同一 `idempotency_key` の再送は課金・送金を再実行せず、初回と同じ結果を返す（ヘッダ `Idempotent-Replayed: true`）。ネットワーク再送やBot再起動での二重払いを防ぐ。

### 3.2 `POST /payout/batch`（一括付与）

イベント配布・デイリー報酬などで多人数へ一度に付与する。

```json
{
  "idempotency_key": "batch-2026-07-23-daily",
  "items": [
    {"user_id": 111, "amount": 500, "kind": "reward"},
    {"user_id": 222, "amount": 500, "kind": "reward"}
  ]
}
```

- レスポンスは各要素の成否を配列で返す（部分失敗を許容）:

```json
{
  "results": [
    {"user_id": 111, "status": "ok", "payout_id": 91101},
    {"user_id": 222, "status": "error", "error": "user_banned"}
  ],
  "company_balance": 24000
}
```

- 全体の合計が準備金を超える場合は、可能な分だけ処理するか全体を拒否するかを明記（推奨: 事前に合計をチェックして超過なら `400`）。

### 3.3 `GET /payouts?since=<id>&limit=<n>`（履歴・任意）

払い出し履歴をカーソル式で取得（`/payments` と対称）。会計突合・監査に使用。

```json
{
  "payouts": [
    {"id": 91021, "user_id": 123456789, "amount": 4600, "kind": "withdraw", "at": "2026-07-23 12:00:00"}
  ],
  "next_cursor": 91021,
  "count": 1
}
```

### 3.4 入金 Webhook（push・任意）

`/payments` ポーリングの代替。会社が登録したURLへ入金イベントをPOSTする。

- ペイロード例: `{ "id": 40213, "user_id": 123, "amount": 5000, "reason": "company_payment", "at": "..." }`
- **署名検証**（共有シークレットのHMAC等）、**再送**（2xxを受け取るまでリトライ）、**冪等キー**（`id`）を備える。
- 低遅延・低負荷。採用してもポーリング(`/payments`)はフォールバックとして併存可能。

### 3.5 `GET /users/{user_id}/balance`（ユーザーのグローバルよあコイン残高・要望）

Botの `/balance` で**ユーザー本人の実よあコイン残高**を表示したい。現状、一般会社が任意ユーザーのよあコイン残高を取得する手段が無い（`/company` は自社資金、`/chips/{id}` はカジノのチップのみ）。

- 認証: 既存 `Authorization: Bearer`。
- レスポンス例: `{ "user_id": 123456789, "balance": 12345 }`
- プライバシー配慮: 自社と取引のあるユーザーに限定する等の制限は開発者判断で可。
- 用途: 残高表示のみ（移動はしない）。読み取り専用。

### 3.6 `POST /charge`（ユーザー→会社の課金・任意）

`/payout`（会社→ユーザー）の**逆方向**。ユーザーの同意のもと、ユーザーのよあコインを会社へ移す。これがあると「`/exchange` でよあコイン→リリーをスラッシュコマンドで即時実行」「ジェムを実よあコインで購入」が可能になる（現状は `y!` 送金＝入金でしか よあコイン→社 の移動ができない）。

- body: `{ "user_id", "amount", "idempotency_key" }`、冪等必須。
- **ユーザー同意**が要点（誤課金防止）。実装形態は開発者判断（例: ユーザーが承認するフロー、事前承認枠など）。
- 無ければ「よあコイン→リリー」「ジェム購入(よあコイン)」は入金(y!)経由に限定される。

## 4. エラー仕様（既存に合わせる）

| コード | error | 説明 |
|--------|-------|------|
| 400 | `insufficient_reserve` | 会社資金（準備金フロア）を超える付与 |
| 400 | `invalid_amount` | amount <= 0 等 |
| 401 | `unauthorized` | キー不正・期限切れ |
| 403 | `user_banned` | 受取ユーザーが経済BAN中 |
| 404 | `not_found` | 会社/ユーザー不明 |
| 5xx | `server_error` | サーバ側エラー（リトライ可） |

レスポンスは既存同様 `{"error": "reason"}`。

---

## 5. セキュリティ / 健全性

- 会社ごとにサンドボックス分離（既存方針を踏襲）。他社ユーザーへは付与できない。
- **準備金チェック必須**（`company_balance - amount >= reserve_floor`）。会社が設定可能な下限フロアが望ましい。
- レート制限（例: 秒間数回）と1回あたりの上限額。
- 監査ログ（`GET /payouts`）で入出金の突合を可能に。
- Webhookは署名検証・再送・冪等で不正/欠落を防止。

---

## 6. 経済ガイダンス（開発者向け補足）

- **報酬を実よあコインで配ると会社資本は減る**方向に働く。健全性を保つには、①ユーザーがゲームで使う額（sink）が配布額（grant）を上回ること、②`/payout` が必ず**準備金フロア**を守ること、の2点が要。
- 上記「内部残高モデル」を採ると、報酬と消費が残高内で相殺され、**実送金＝出金時のみ**になるため、会社資本の目減りを最小化できる（当Botはこの方式で「会社資本 30,000→50,000」の黒字運用を成立させている）。

---

## 7. Bot側の対応状況

- クライアントに `payout()` / `payout_batch()` / `payouts()` を実装済み（`api/yoacoin_client.py`）。
- フィーチャーフラグ `PAYOUT_ENABLED` でON/OFF。
  - `true`（API採用後）: `/cashout` 実行時に `POST /payout`（`kind="withdraw"`）を呼び、成功後に内部コインを焼却。
  - `false`（既定）: 内部コインを焼却して**出金申請キュー**に積み、運営が確認後に手動送金（暫定運用）。
- 採用いただければ、Bot側は**フラグを立てるだけ**で即対応できます。

---

## 8. 提案の粒度（優先順位）

1. **最優先: `POST /payout`**（冪等・準備金チェック）。これだけで「報酬付与」と「換金」の両方が成立。
2. あると嬉しい: `POST /payout/batch`（イベント配布）、`GET /payouts`（監査）。
3. 将来的に: 入金Webhook（低遅延化）。

命名やフィールドは既存APIの慣習に合わせて調整いただいて構いません。まずは `POST /payout` からのご検討をお願いします。
